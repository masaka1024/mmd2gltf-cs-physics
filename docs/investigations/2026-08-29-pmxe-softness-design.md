> 前提: タスク100 (H2''。戻し速度 `a` は三者同等で、差は `d̄_sat` にしか出ない。

## 0. 何を手掛かりにするか (タスク100 の数値、再掲)

| 条件 | `d̄_sat` 参照 | `d̄_sat` 当エンジン | `d̄_sat` bulletref | `a` 参照 / 当エンジン / bulletref |
|---|---|---|---|---|
| flat (一様 5.559e14) | **0.002958** | 0.000740 | 0.000766 | 0.92165 / 0.91700 / 0.90287 |
| ladder (段差 1/3) | 0.000065 | 0.000024 | 0.000022 | 0.85436 / 0.83173 / 0.83218 |

**探すのは「`bulletref` の `d̄_sat` を 0.000766 から 0.002958 へ 4 倍緩める軸」。**
同時に `a` を壊さないこと (参照 0.92165 の ±20% に留まること) が条件。

### ★先に片付ける基準の非対称 (本設計の起点であり、タスク100 の但し書きに追記が要る)

`bulletref.cpp:779` の `if (erp >= 0)` により、**`--erp` を渡さない走行では joint の ERP が
Bullet 自身の既定 (linear `m_restitution` 0.5 / angular `m_ERP` 0.5) のまま**である。
`net.txt` の `beta=0.2` は**読み込まれるが適用されていない** (`bulletref.cpp:216` で parse、適用箇所なし)。
一方 **当エンジンは `Joint.Beta = 0.2`**。

- つまり タスク99 / タスク100 の `bulletref` 腕は、**joint ERP が当エンジンと違う条件で走っていた**。
- それでも `a` は当エンジンと 0.5〜1.5% 差で一致した。→ **この領域で `a` は joint ERP にほぼ鈍感**。
- ★**この非対称は第1部の軸 (E1) として正面から扱う**。同時に、
  **タスク100 の但し書きへ「bulletref 腕の joint ERP は 0.5 (Bullet 既定) だった」を追記する**
  (数値の撤回ではない。条件の記載漏れの補正)。

# 第1部 (主): `bulletref` で参照を再現する探索

## 1-1. 走行の規約 (取り違え番人)

1. **1回の走行で動かすのは 1 軸のみ。** 2 軸同時は、1 軸単独で全滅した後の第2ラウンドでのみ行う。
2. **各バッチの先頭に「基準構成の再現走行」を必ず置く。**
   `--substeps 2 --iters 10 --nocontact`・`--erp` なし = タスク100 と同一。
   出力 `net_bullet_state.csv` の **md5 が タスク100 の記録値と一致**すること。
   一致しなければ**そのバッチは破棄**する (構成の取り違え・ビルド差の検出)。
3. `net.txt` と `drive.csv` は **タスク100 で書き出したものを再利用**する (再エクスポートしない)。
4. **`bulletref` は診断用途なので構成変更してよい。** ただし変更は
   「solverInfo のフィールドを CLI から触れるようにする」までとし、**ソルバの式には手を入れない**。
   `bullet-2.75/src` は 1 行も変えない (既存の規約)。

## 1-2. 候補軸の事前列挙

減衰 (`lindamp`/`angdamp`)・質量・慣性。**これらは試料を変える**ので、
「PMXe が何を緩めているか」の答えにはならない。**陰性対照としてのみ使う。**

★**接触なし (`mask=0x0000`) の系なので、A3 / B1 / B2 / B3 は原理的に効かないはず。**
**効かないことを確認する陰性対照として回す。** ここで何かが動いたら、それは
「接触が無いはずの系に接触が入っている」という**計測系の故障**の印であり、先にそれを潰す。

## 1-3. 判定量と合格基準 (事前登録)

- 判定量は **`d̄_sat`** と **`a`**。定義・窓・フィットは **v1.2 計器 (`masschain_cmp_v12.py`) をそのまま流用**。
- **flat / ladder の両条件**で出す。片方だけの一致は採らない。

> ### ★合格基準
> **`d̄_sat` が参照の ±30% に入り、かつ `a` が参照の ±20% に入る軸**
> (**単独、または 2 軸まで**の組合せ) が見つかれば、それを **「PMXe の緩め方の候補」** とする。
>
> - flat: `d̄_sat` 0.002958 の ±30% = **[0.002071, 0.003845]** / `a` 0.92165 の ±20% = **[0.73732, 1.10598]**
> - ladder: `d̄_sat` 0.000065 の ±30% = **[0.0000455, 0.0000845]** / `a` 0.85436 の ±20% = **[0.68349, 1.02523]**
> - **両条件を同時に満たすこと。** 片方だけなら「部分一致」として記録し、候補にはしない。
> - 3 軸以上の組合せは**採らない** (自由度が多すぎて当てはめになる)。

## 1-4. 全滅時の記録形式 (事前登録)

どの軸も基準を満たさなかった場合、**「見つからなかった」で終わらせず、次の形で記録する**:

```
[軸ごとの表]  軸 / 振った値 / flat d̄_sat / flat a / ladder d̄_sat / ladder a / 参照との比
[単調性]      その軸で d̄_sat は単調に動いたか。動いたなら参照へ届くのに必要な外挿値は幾つか
[到達不能の型] (i) 動かない (陰性対照どおり) / (ii) 動くが参照へ届かない (外挿値が非現実的)
              (iii) d̄_sat は届くが a が壊れる  ← どの型かを軸ごとに明記する
[結論]        「この系で振れる範囲に、参照の緩さを説明する単一軸は無い」
```

★**(iii) の型が出た軸は、実は最も情報量が多い**。「緩められるが、緩めると戻し速度も壊れる」=
**PMXe は `d̄_sat` だけを選択的に緩めている**ことになり、単純なソルバ設定では説明できない、という
強い所見になる。**必ず型を分けて記録すること。**

## 2-4. 第1部で軸が見つかった場合の対応確認 (手順のみ)

1. 見つかった軸 X (例: `--iters 4`) を **`bulletref` 側で固定**する。
2. **当エンジン側に対応する設定があるか**を表で突き合わせる (`--iters` ↔ `ITERS` など)。
3. 対応があるなら、**当エンジンを同じ値にして走らせ**、`d̄_sat` / `a` が同じ向きに動くかを見る。
   - **同じ向きに動く** → その軸は「PMXe の緩め方」の共通表現として妥当。次段は**その軸の既定値の再考**へ。
   - **動かない** → 同名でも実装が違う。**行レベル突合の対象が1つに絞れた**ことになる。
4. 対応が無い軸 (例: `m_globalCfm`) なら **§2-3 の freeze 明け候補へ積む**。**実装はしない。**

# 末尾: 分岐 (事前登録)

> **第1部で軸が見つからなかった場合 (P4 / P5)**、次段は
> **「モデルZ 実機の要素をプローブへ持ち込む設計」**へ進む。
>
> 持ち込む要素は 2 つ:
> 1. **長鎖 (35 リンク)** — 現行プローブは 3 リンク。**鎖長そのものが効く**可能性がある
>    (逐次インパルスの伝播は鎖長に対して劣化する)。
> 2. **激しい駆動** — 現行は段差 1 回。実機はダンス全編で、`d` の水準が桁で違う。
>
> ★ただし**一度に両方は持ち込まない。** 「3リンク→35リンク」だけを変えた版を先に作る。
> 段差駆動は据え置く。**1 度に 1 つ**という本設計の規約を、分岐先でも守る。
>
> **この分岐に入る場合は新規ベイクが要る** (長鎖プローブ 1〜2 本)。
> ベイク依頼はその設計が承認されてから。
