# Unity Bullet互換物理エンジン設計

## 概要
PmxEditor(極北P)のBullet 2.75準拠物理(剛体・Joint・SoftBody)をUnity C#で再実装。
PMX 2.1仕様に準拠したMMD物理演算エンジン。外部ネイティブ依存なし。

## Bullet 2.75 の接触ソルバ既定値 (2026-08-08 調査)
MMD / PmxEditorが依拠する Bullet **2.75** の `btContactSolverInfo` 既定値
(vancegroup-mirrors/bullet-physics `bullet-2.75` タグのソースで確認):

| 項目 | 2.75 | master(参考) | 2.82(参考) |
|---|---|---|---|
| `m_splitImpulse` | **false** | true | true |
| `m_splitImpulsePenetrationThreshold` | **-0.02** | -0.04 | -0.04 |
| `m_erp` | 0.2 | 0.2 | 0.2 |
| `m_erp2` | 0.1 | 0.2 | 0.8 |
| `m_splitImpulseTurnErp` | **無し(未実装)** | 0.1 | 0.1 |
| `m_numIterations` | 10 | 10 | 10 |

- **2.75 では Split Impulse は既定 OFF**。2.75 の `convertContact` の split 経路は、
  位置補正インパルス (`m_erp` で計算) を「速度側 rhs に足す」か「擬似側 rhsPenetration へ回す」かの
  振り分けのみで、**接触の split には erp2 を使わない** (erp2 はジョイント側 ERP)。
- したがって、MMD が 2.75 既定のままならMMDも Baumgarte-in-velocity (当方の従来方式) 相当であり、
  Split Impulse 化がMMDへ「近づく」保証はない。**MMD が既定を上書きしているかは未確認**。
- なお master/2.82 では既定 true。効果検証の価値はあるため、当方でも実装して測る方針とする
  (実装と測定結果は別コミット)。

## 本体是正 (2026-08-08)
- 物理開始時の FK-rest リセット (MMD の物理演算リセット相当) を実装:
  `PmxPhysicsBuilder.ResetBodiesToBonePoseFk(getDrivenBoneWorld)` が、動的剛体を含む全剛体を
  ボーンの FK-rest ワールド姿勢 * `BodyOffsetFromBone` へ置き、速度0・慣性ワールド更新・接触
  (蓄積インパルス)クリアを行う。FK-rest = 親駆動のバインド整合姿勢で、物理ボーン(動的剛体が
  紐づくボーン)は外部姿勢を使わず親チェーンから前計算する(バインドは位置のみ・回転恒等)。
  `PmxReader` にボーン親(と変形階層)を保持させた(従来は Skip)。
  配線: HeadlessDriver/BonePoseCsvPlayer/MmdPhysicsBehaviour。
  - **背景**: 従来は `BuildBodies` が全剛体をバインド位置に置き、その後 kinematic 剛体だけが
    フレーム0姿勢へ動くため、フレーム0で脚が曲がっていると太ももコライダーだけが動き、
    動的スカートがバインドに取り残されて逃げられない貫入平衡(初期4秒, 深さ~1.18)に落ちていた。
  - **効果**(下記「新ベースライン」): 初期貫入を完全解消(スカート_1_5×左太もも F0-120: 1.166→0.0001、
    全編で貫入>0.5 のフレーム 129→0)。傾き統計はほぼ不変(平時中央 10.46→10.41)。
    **開始状態が正しくなれば warmup=0 でも成立**する(従来の「初期貫入は warmup で解ける」という
    想定は誤りだった=warmup を 60→3000 に増やしても初期貫入は減らなかった)。
- Split Impulse (接触の貫入回復を実速度から分離) を実装 (`UseSplitImpulse`, **既定 false**):
  剛体に擬似速度 (Pseudo Linear/Angular = btRigidBody の pushVelocity/turnVelocity 相当) を持たせ、
  貫入が閾値 (-0.02) より深い接触の位置補正を、実速度とは別の反復で擬似速度に対して解く。
  位置積分は「実速度+擬似速度」で進め、擬似速度は速度として残さない。反発は実速度側に維持、
  ジョイント ERP(Beta) は不変。浅い貫入は従来どおり速度側 Baumgarte。`false` で従来と**ビット一致**。
  - **測定結果: 過大スイング仮説 (Baumgarte のエネルギー注入が原因) は不支持**。
    - 12窓の比(自前/MMD)の中央値: 1.133→1.112 (微小)。窓別は混在し、窓1/7/12 は改善だが
      **窓6(1.19→1.37)・窓10(1.31→1.38)・窓3(1.08→1.13)は悪化**。
    - **反復数依存は弱まらない** (決め手): 窓ピークmax は off/on とも iters 3→10 で増加
      (off 62→88, on 69→86)、iters=1 は両者過大 (110/118)。split-on は split-off をほぼ追従。
    - 平時中央 11.041→10.797 (微減)、貫入平均 0.0695→0.0531 (改善)・最大は微増、
      ノイズフロア 0 維持、性能 +0.015ms(無視可)、回帰全PASS。
  - **判断: 既定 false を選択** (2.75 準拠・旧ベースライン 11.041/22.498/111.822 を維持)。
    実装は比較用に温存し、`UseSplitImpulse=true` でいつでも切替可能。
    (参考: 既定 true とした場合の平時統計は 10.797/21.851/113.018 だった。)
- 接触制約の解く順序を決定化: `BuildContactConstraints` が `_manifolds` (Dictionary) を
  列挙する順序は挿入/削除履歴に依存し非決定的だった。剛体indexの組 (PairKey) の昇順に
  並べ替えてから制約を構築するよう変更 (再利用バッファ `_sortedManifolds` でソート)。
  式・パラメータは不変、**順序のみ**。これにより「スカートに一切触れない無関係な剛体の
  増減」で接触の解く順序が変わり結果が揺れる現象 (Gauss-Seidel の順序依存) を排除した。
  マニフォールド内の接触点順序は元々 List を index 走査で管理し決定的、Joints/Bodies も
  PMX定義順で安定。結果順序に影響する非決定要因は本 Dictionary 列挙のみだった
  (`seen` HashSet は集合判定のみ、SoftBody の HashSet/Dict はビルド時トポロジ、
   `MmdPhysicsBehaviour` の名前マップは引き専用で、いずれも結果順序に非関与)。
  ※順序が変わるため数値は変化する (下記「以降の比較基準」に新ベースラインを記録)。
    MMDに近づけるための変更ではなく、測定器の再現性を上げるための変更である。

- 剛体 -> RigidBody (btRigidBody)  形状 0:球 1:箱 2:カプセル
- 物理演算タイプ 0:ボーン追従(kinematic) 1:物理(dynamic) 2:物理+Bone位置合わせ
- Joint種類0: ﾊﾞﾈ付6DOF -> btGeneric6DofSpringConstraint
- Joint種類1: 6DOF -> btGeneric6DofConstraint
- Joint種類2: P2P -> btPoint2PointConstraint
- Joint種類3: ConeTwist -> btConeTwistConstraint
- Joint種類4: Slider -> btSliderConstraint
- Joint種類5: Hinge -> btHingeConstraint

- 衝突グループ: PMX の16bitは「衝突する相手グループ」のマスク(bit=1で衝突)。
  Bullet の (groupA & maskB) && (groupB & maskA) で判定

## 時間刻み (リファレンス: 実効 1/60)
**`MmdPhysicsBehaviour` の既定は `FixedTimeStep = 1/60`, `SubSteps = 1`**(実効刻み 1/60)。
`PhysicsWorld` 単体の既定は `1/30 × 2` で実効刻みは同じ。

1/60×1 は 1/30×2 と実効刻みが同一で忠実度も数値まで一致する
(bonecheck 傾き中央11.20 / p90 23.52 / 12窓比1.0611 が同値)が、**Unity の Time.fixedDeltaTime と
一致するため毎FixedUpdateでちょうど1ステップ進み、更新間隔が等間隔になる**(コマ落ちが消える)。
`AlignUnityFixedTimestep`(既定ON)が起動時に Time.fixedDeltaTime を自動整列する。

### 旧「30Hz・1サブ」は未検証の仮定であり、誤りだった
以前の既定 `SubSteps=1`（実効1/30）は「MMDは 30fps で 1描画フレーム=1物理ステップ」
という**当方の未検証の仮定**に基づいて置いたもので、検証の結果その仮定は誤りと判明した。
外部の MMD 互換実装はいずれも当方より細かい刻みを使っている（ソース確認）:
- **Saba**: `stepSimulation(t, maxSubSteps=10, fixedTimeStep=1/120)`（既定 fps=120）。
- **libmmd**: `stepSimulation(step, maxSubSteps=60)`（fixedTimeStep 既定 1/60）。
- solver 設定はいずれも Bullet 既定（`m_numIterations=10` 等）を上書きしない。
- MMD 本体は「物理を最大60fpsで演算」との公開情報あり（[出典](https://x.com/Baroque384/status/1327403875662393345)）。
- **MMD本体・PMXエディタ（ベイク生成元）の正確な `fixedTimeStep` は未確認**。

### 刻み掃引の実測（反復10固定・modelA.pmx・12窓比の中央値, MMD=1.0目標）
実効刻みを細かくするほどMMDのスカート傾きに一致する（過大スイングが解消）:

| 実効刻み | 分割 (SubSteps経路) | 12窓比中央 | 平時中央 | 貫入平均 |
|---|---|---|---|---|
| 1/30 | Sub1（旧既定） | 1.133 | 11.04 | 0.070 |
| **1/60** | **Sub2（新既定）** | **1.030** | 10.46 | 0.032 |
| 1/120 | Sub4 | 0.978 | 10.89 | 0.024 |

**1/60（Sub2）を採用**。理由: 1.030 と 0.978 はMMDとの差3%以内で微過大/微過小の違いに過ぎず、
0.978 を選ぶのは「1.0に近い方」への曲線当てはめに寄る。根拠面では、Saba の 1/120 は一実装の選択に
すぎないのに対し「MMD本体が物理を60fpsで扱う」はMMD側の性質であり、リファレンスが PMXエディタの
ベイクである以上 MMD 系の刻みに寄せる方が筋が通る。性能も Sub2 は Sub4 の半分（0.65 vs 1.2 ms/step）。
**将来より忠実度を上げたい場合は SubSteps=4（実効1/120, 12窓比0.978）が選択肢**として残る。

### 細刻み化は SubSteps で行う（FixedTimeStep 経路は使わない）
同じ実効刻みでも `FixedTimeStep` を下げる経路（accumulator が1フレーム内で InternalStep を複数回
呼ぶ）と `SubSteps` を上げる経路で結果が大きく違った（1/60: FTS経路1.233 vs Sub経路1.030）。
原因は**キネマティック（ボーン）目標の補間バグ**で、FTS-accumulator 経路では各 InternalStep が
「現在位置→フレーム目標」を端点にするため、最初の内部ステップで目標へ N倍速でジャンプ→残り停止し、
30fps 入力を正しく細分できていなかった（残存velx=0）。**この補間を InternalStep を跨いで
フレーム全体で連続させる修正を実施済み**（本体是正・タスクA。フレーム総サブステップ数を分母に
等分補間）。修正後は両経路とも 1フレーム内を等速移動する（残存velx=30、回帰テスト化）。
それでも入力は 1/30 境界でしか更新されないため、忠実な細分は SubSteps 経路を使う。

## 座標系
エンジンはPMXネイティブ座標で計算。Unity境界(MmdPhysicsBehaviour)の変換は
**単位スケールのみで、軸反転は無い**(真の等長変換)。重力はMMDスケールで約 -98 (= -9.8 * 10)。

    MmdToUnityPos(v) = (v.x, v.y, v.z) * UnitScale
    MmdToUnityRot(q) = (q.x, q.y, q.z, q.w)      // 恒等

mmd2gltf(PMX→glTF) と UniGLTF(glTF→Unity) の ReverseZ が二重に掛かって相殺するため、
Unity側のボーンは既にPMXネイティブ座標値になっている。かつてここに3回目のZ反転があり
鏡映(det=-1)になっていた(髪が正面へ反転して体を貫通する症状)。2026-08-09 に除去 (9e90801)。

### オイラー角の順序 (2026-08-10 修正)
PMX の剛体/Joint 回転は **YXZ 順 (R = Ry·Rx·Rz)**。Bullet の `btQuaternion(yaw,pitch,roll)` と同型。
`Quat.FromEulerYxz` を使うこと。`Quat.FromEuler` は ZYX 順なので **PMXデータには使わない**。
従来 ZYX で解釈しており、複合回転の強い剛体で向きがズレていた
(髪カプセル402本の中央値 2.3°→0.0°)。詳細は investigations/2026-08-10-multi-model-defects.md。

## 試して破棄した方針 (再挑戦しないための記録)

### 物理リセットで CSV姿勢(MMDの物理結果)を全剛体へ一斉適用 — 破棄
物理開始時のリセットで、CSV(MMDベイク=物理結果, 傾き込み)のボーン姿勢を動的スカートにも
そのまま適用したところ**発散**した(平時中央 10.46→**25.34**、12窓比 1.03→**2.85**、傾きmax 178°)。
原因: スカートは横Joint52本で全周が閉ループに繋がっており、36枚を外から一斉にMMD姿勢へ置くと
復元誤差(bone*offset の ~1e-3)で locked-linear 拘束が過剰になり、ソルバがエネルギーを注入して暴れる。
**正解は FK-rest**(親駆動のバインド整合姿勢): 物理ボーンは外部姿勢を使わず親チェーンから前計算する
(バインドは位置のみ・回転恒等)。FK-rest なら閉ループがバインドで厳密整合するため発散せず、
初期貫入を解消しつつ傾きは不変(10.46→10.41, 12窓比 1.03→1.06)。→ リセットの配置姿勢は必ず FK-rest を使う。

### ジョイント行の蓄積インパルス引き継ぎ (warm-start) — 破棄
Bullet準拠 (係数0.85=m_warmstartingFactor) でジョイント制約行のウォームスタートを実装したが悪化。
X角度リミット(±80°)超過 最大 90.9°→111.5°、平時中央値 11.05→11.49。
見立て: 角度リミット行は Euler分解で軸/側が毎フレームトグルするため、引き継いだ力積が
別軸/別側へ適用され復元でなく擾乱になる。
※接触の PersistentManifold ウォームスタートは有効なままで、そちらは変更しない。

### バネのモーター化 (2-b) — 実装せず打ち切り → ★2026-08-22 撤回・採用済み
バネをBullet同様のソルバ反復内モーターへ変える案は、対象モデル(モデルA)のスカートJointが
バネ未使用 (SpringAngular=SpringLinear=0, 制御は角度リミットのみ) のため効果ゼロと判明し、打ち切った。
(参考: 6DOF バネには粘性項が無いことを確認し、当方の `-SpringDamping*k*relVel` 粘性項は除去済み。)

**★この打ち切り判断は誤りだった。** 「効果ゼロ」は **モデルA がばねを使わない唯一のモデル**
だったことによる観測の欠落であって、方式の否定ではない。ばね持ちモデルで測り直したところ
単一施策として最大の改善が出たため、2026-08-22 に `Joint.SpringAsMotorRow` として実装し既定にした
→ 「バネのモーター行化 (SpringAsMotorRow) の採用」の節。
**教訓: 1モデルしか見ずに方式を却下しない。** 判定に使うモデルがその機構を使っているかを先に確かめる。

### 角度行のインパルス軸を Bullet 風混合軸へ (破棄)
`Constraints.cs` の角度リミット行の軸を、A のフレーム列(直交)から
Bullet の `btGeneric6DofConstraint::calculateTransforms` 風の混合軸
(A.Z と B.X 由来、一般に非直交) へ変える案を試したが、**全体的に悪化**したため破棄した。
- modelA.pmx で 平時中央値 11.05→13.09、窓の(自前/MMD)傾きmax比の中央値 1.12→1.5 と悪化。
  ほぼ全窓で悪化 (窓1: 81.5→164.7 など)。ring2 の1フレームスパイクも消えなかった。
- 推測: 非直交軸は角度行同士がカップリングし、逐次インパルス(Gauss-Seidel 10反復)では
  直交軸より収束が悪い。加えて Bullet の `m_calculatedAxis[i]` と `matrixToEulerXYZ` の
  (x,y,z) 対応順序をソース未確認のまま実装したため、軸と誤差値の対応がずれていた可能性。
- 未確認: Bullet 2.75 が非直交軸をソルバでどう条件付けしているか。

### 最小再現の落とし穴: 真下向きチェーンは退化配置 (2026-08-09)

`tools/chainbug` (TASK=1)。

### 投機的接触は (b) 方式
接触生成には投機的マージン `SpeculativeMargin = 0.02` を用いるが、押し出し方は
本来の投機的接触 (b) である。すなわち非貫入 (`Distance > 0`) の接触では目標接近速度を
`-Distance/dt` とし、「このステップで表面へちょうど到達する接近」までは許して
貫入だけを止める。**クリアランスは膨らまない** (接地する球はマージン分浮かず真の接触面で静止)。
マージンの役割は「表面が触れる少し手前から接触を連続的に検出し、貫入 on/off の
振動を防ぐ先読み」であり、静止物体を押し離す力にはならない
(重力0・1ステップで非貫入接触への法線インパルスは0件。回帰テストで監視)。

### 初期条件感度 (背景ノイズとしての軌道分岐)
`SpeculativeMargin` を 0→0.02 に変えると、重力0・300ステップでの動的剛体の
平均変位が **0.2086 → 0.2649** (差 **0.076 unit ≒ 9.5mm**) 分岐する。
これは**クリアランス膨張ではなく**、検出バンド幅が広がることで
バインドポーズの初期貫入を解消する過渡により多くの投機拘束が働き、
軌道が分岐する**カオス的発散**である (差はマージンに対し劣線形。膨張なら線形のはず)。
**パラメータの効果を評価する際は、この程度 (~0.08 unit) の軌道分岐が
背景ノイズとして常に存在することを前提に判断すること。**

### 刻みによる貫入量 (30Hz・1サブ vs 60Hz・2サブ)
modelA.pmx (剛体117) 300ステップ・重力-98 での貫入量:

| 刻み | 貫入 平均 (貫入接触のみ) | 貫入 最大 |
|---|---|---|
| 30Hz・1サブ (既定) | 0.0561 | 1.023 |
| 60Hz・2サブ | 0.0288 | 0.845 |

30Hz は1ステップの移動量が大きい分、平均貫入で約2倍・最大で+21% 深くなる
(想定内)。(b) 投機的接触により、深い貫入でも Baumgarte の暴発 (エネルギー注入) は
起きず NaN・速度爆発なしで回復する。EPA上限hitも0。

### リファレンス刻み
既定は実効 1/60（FixedTimeStep=1/30・SubSteps=2）。以前の「30Hz・1サブ」は未検証の仮定で
誤りだったと判明し、刻み掃引の実測（12窓比 1/30:1.133→1/60:1.030→1/120:0.978）と外部実装の
慣行（Saba=1/120, libmmd=1/60, MMD物理最大60fps）に基づき変更した（「時間刻み」節参照）。

### 測定のノイズフロア (カオス感度と、順序決定化後の実測)
系は Gauss-Seidel 逐次インパルス+接触の連鎖でカオス的であり、拘束を**解く順序**に敏感である。

- **順序決定化 (2026-08-08) 以前**: 接触は Dictionary 列挙順で解かれ、その順序は挿入/削除
  履歴に依存した。このため**スカートに一切触れない無関係な剛体を足す/慣性を変えるだけ**でも、
  スカートの窓ピークが最大 **8.4°** (平時中央 2.3°) 揺れた。これは物理ではなく**測定器の
  非決定性**だった (例: カプセル慣性のBullet準拠化でスカート窓ピークが ~8° 動いた件)。
- **順序決定化 (PairKey昇順) 後の実測ノイズフロア = 0**。遠方ダミー動的剛体(x=100000, 球6+床)の
  有無で、スカート統計 (平時・12窓ピーク) は**完全一致** (最大差 0.0000)。カプセル慣性を
  円柱式↔外接箱式で切替えてもスカートは完全一致 (11.041/22.498/111.822 で不変)。
  → **スカートの接触・軌道を実際には変えない変更に対し、測定ノイズはゼロ**になった
    (`tools/diagnostics/determinism` の検証1で監視)。

- **ただしカオス感度そのものは消えていない**。スカート自身の接触・軌道を**実際に変える**変更
  (スカートに触れる剛体、スカートに効くパラメータ、初期条件) に対しては、上記「初期条件感度」
  の ~0.08 unit の軌道分岐が依然として本質的に存在する。これは測定器ノイズではなく系の性質。

- **この幅を下回る改善は、単発の測定では判定できない**。窓ピーク(40〜90°)基準では
  順序ノイズ除去後もカオス由来の感度が残るため、微小改善の判定には注意する。

- **判定したい場合の推奨手順** (今回実際に有効だったもののみ):
  1. **同一バイナリ・同一入力で変更前後を測り差を見る**。順序決定化済みなので、無関係経路の
     ノイズは乗らず、差は純粋に変更由来となる。
  2. **効果が疑わしいときは遠方ダミー剛体テスト (Det.cs 検証1) で切り分ける**。ダミー有無で
     差=0 なら、その変更はスカートの物理を変えていない (測定経路の差でしかない) と判る。
  3. **窓ピークより中央値で比較する**。中央値はカオス感度の高い尾より安定で、実験を通じて
     変更に対する振れが小さかった。

## 既知の逸脱: 求解順序 (SolveJointsFirst, 2026-08-09)
Bullet 2.75/2.83 solveSingleIteration は 1反復内で NonContact(ジョイント)→接触→摩擦 の順に解く
(接触が後勝ち, 実ソース確認済)。**当エンジンの既定は逆で「接触→ジョイント」(ジョイントが後勝ち)**。
これは **Bulletとは異なると判明している既知の逸脱**であり、「こちらの順序が正しい」わけではない。

- 現状ONにしていない理由: MMD(補正ON, PMXエディタ)との忠実度で、既定順(逸脱)の方が近い
  (12窓比 中央: 既定1.061 vs Bullet同順1.190。既定の方がMMDに近い)。経験的にMMDに近いため**暫定維持**。
- ★重要な留保: 12窓比1.061という良い数字は、**誤った順序が過スイングを偶然抑え込んでいるだけの可能性**がある。
  この可能性は消さない。フラグ `PhysicsWorld.SolveJointsFirst` (既定false) で温存し、
  **貫入欠陥(下記)を直した後にMMD距離で再評価する**。
- 参考: SolveJointsFirst=ON で深貫入 17,407→2,241(7.8×改善)。ただしMMDからは離れる(トレードオフ)。

## 既知の逸脱 一覧 (Bulletと異なると判明したが暫定維持しているもの)
増える場合、それ自体が「どこかで根本を取り違えている」信号。正当化せず一覧管理する。
1. **求解順序 SolveJointsFirst=false** (2026-08-09): Bulletは1反復内で ジョイント→接触(接触が後勝ち)。
   当エンジン既定は逆(接触→ジョイント)。MMD(補正ON)には既定順の方が近い(12窓比1.061<1.190)ため暫定維持。
   ★12窓比の良さは誤順が過スイングを偶然抑えている可能性を含む。貫入修正後に再評価。
2. **接触warm-start係数 ContactWarmStartFactor=1.0** (2026-08-09): Bulletは 0.85 (m_warmstartingFactor)。
   当エンジン既定 1.0。実測で 0.85 は深貫入を悪化(JOINTS_FIRST 2241→7109)させたため 1.0 を暫定維持。
   ★「1.0が正しい」わけではない。持続接触で満額warm-startが効いて見えるだけの可能性。貫入の根本解明後に再評価。
3. **接触の受理閾値 Collision.SpeculativeMargin=0.02 の固定距離** (2026-08-22): Bullet 2.75 は
   **ペアごとに形状サイズ比例**。`min(shapeA,shapeB)` の
   `getContactBreakingThreshold() = getAngularMotionDisc() * gContactThresholdFactor(=0.02)`
   で、`getAngularMotionDisc()` は単位変換 AABB の半対角 + |中心|。
   実測差: 半幅(0.347,0.371,0.200) のスカート箱で Bullet 0.0109 に対し当方 0.02 = **当方が約2倍広い**。
   分離しているペアまで接触に上げている。`GjkEpa.BulletContactThreshold` で A/B できる (既定OFF)。
   ★静止スカートに**効く**。モデルB は参照比 3.84× → 1.37×、モデルA も −24%。
     ただし**モデルP は +140% と退行**するためモデル依存。採否は 31モデルスイープの後。
4. **linear slop PenetrationSlop=0.005** (2026-08-21): Bullet 2.75 は `m_linearSlop = 0.0`。
   0 にすると静止スカートが悪化する (モデルA +33% / モデルP +174%) ため現状維持。
5. **ブロードフェーズが軸ごとAABBではなく境界球** (2026-08-23): Bullet の
   `btCollisionWorld::updateSingleAabb` は **形状の軸ごと AABB** (カプセルは
   `(r, hh+r, r) + getMargin()`) に `gContactBreakingThreshold = 0.02` を各軸へ足す。
   当エンジン `RigidBody.ComputeAabb` は **中心まわりの境界球** `BoundingRadius + Margin` で、
   カプセルでは `hh + 2r` になる。しかも `BroadphaseNarrowphase` の追加膨張は
   `SpeculativeMargin - SpeculativeMarginDefault` = **0** なので 0.02 も足していない。
   実測 (モデルA 髪):
   | 剛体 | Bullet AABB 半幅 +0.02 | 当方 境界球 半径 |
   |---|---|---|
   | 髪FL3 | (0.49, 1.63, 0.49) | **2.04** |
   | 右太もも | (1.07, 1.76, 1.07) | **2.75** |
   → **ペアが Bullet より遥かに長く生き残る**。ペア消滅→マニフォールド解放の連動自体は
   当エンジンにも在る (`BroadphaseNarrowphase` の「消えたペアを掃除」) ので、
   欠けているのは**連動ではなく AABB の大きさ**。
   ★ただしタスク66 の机上計算では、**幻の接触行 22/22 は Bullet の AABB でもまだ重なっている**
     ので、これを直しても幻は 1 件も消えない。**逸脱としては登録するが、幻の原因ではない。**

### 形状マージンの逸脱は「原因ではない」と確定 (2026-08-22)
| 形状 | 当エンジン | Bullet 2.75 |
|---|---|---|
| 箱 | `最小半幅 * 0.04` | **0.04 固定** (`CONVEX_DISTANCE_MARGIN`)。`setSafeMargin` は 2.75 に**存在しない** — 後年の Bullet で追加された機能なので、これを 2.75 の仕様として引くのは誤り |
| カプセル | `Margin = 半径` (コア = 線分) | `Margin = 0.04`、コア = 線分 + (半径 − 0.04)。**外形はどちらも 線分+半径 で一致**。差が出るのは `getMargin()` 由来の量 (GJK 探索距離・AABB・受理閾値) だけ |
| 球 | `Margin = 半径` | 同じ (`btSphereShape` も margin=半径) |

`CollisionShape.BulletShapeMargin` で A/B したが、静止スカートは
モデルA・モデルB で**ビット不変**、モデルP で +1.4% と実質無反応だった。
理由: PMX のスカートは箱、脚は カプセルで、当エンジンはこの組を**解析解**で解くため
`Margin` を読まない。箱×箱 は GJK を通るが、同一グループの剛体どうしは
PMX の当たり判定マスクで弾かれるので実際にはペアが立たない。
→ **逸脱としては残るが、揺れの原因ではない。**

### ★角度リミットの実効挙動: 自前は2-5倍硬い (2026-08-09, 格子の答え)
同じ物差し(XYZ euler)で リミット外率/超過量 を3者比較(hairfid):
  取付: 自前 59.8%/超過p90 21.5° | 純Bullet 48.4%/49.5° | MMD(補正ON) 22.8%/14.0°
  縦  : 自前 54.5%/10.3°          | 純Bullet 51.2%/33.8° | MMD(補正ON) 24.7%/7.9°

自前はリミットで止まる(超過10-21°)=実効2-5倍硬い。**
総合像: スカート格子は幾何的に過拘束で、どこかが必ず破れる。純Bulletは「回転」で破れる(パネルが振れて脚を避ける=貫入少)。
自前は「位置」で破れる(パネル直立のまま滑って脚へ=貫入多)。MMD(補正ON)は補正層が破れを最小化。
limitSoftnessは行パス(getInfo2)に登場せず休眠(m_useSolveConstraintObsolete=false)=ソフト化説は否定。
自前の角度行がなぜ硬いか(=純Bulletがなぜ弱いか)の候補は反復収束の差・張り付き時の蓄積のみ。次段はユーザ判断。

## MMD再現のための意図的追加 (Bullet逸脱一覧とは性質が異なるため別管理)
Bulletからの逸脱(上の一覧=「Bulletと違うと判明したが暫定維持」)と異なり、こちらは

## Unity実機「再生中だけスカート貫通」の真因: バックエンド二重稼働 (2026-08-09)
症状: ヘッドレス(深貫入11 vs MMD67)もUnityのBonePoseCsvPlayer(橙わずかのみ)も正常なのに、
Animator再生シーンだけスカートが貫通する。
真因: **PhysXバックエンドが実行中に復活し、自作エンジンと同じボーンを奪い合っていた**。
- `MmdPhysicsBackendSwitch` は Awake でのみ PhysX剛体をパーク(isKinematic=true, detectCollisions=false)。
- 既存インポーターの `MmdPhysicsWarmup.cs:61` が **FixedUpdate で isKinematic=false** に戻す
  (実機ログ「[MMD 始動] 101 個の揺れ物を物理へ引き渡しました（t=0.22s）」)。
- 以後 MmdGravity が108剛体へ加力、MmdCollisionMask が実行時に衝突を復活。
  MmdJointProbe の「円錐到達率 中央880%/最大1236%(sy=-40〜-61° vs limY=5°)」はこの二重稼働の結果を測っていた
  (=我々のエンジンの評価値ではない。ヘッドレスの取付超過は p90 3.4°)。
対策(自分のファイル内で完結, importer非依存): BackendSwitch に `EnforceExclusive`(既定ON)を追加し、
Custom の間は**毎FixedUpdateでパークを再主張**する。初回の再パーク時に1度だけ理由をログする。
教訓: 「排他」を初期化1回で担保しない。相手が実行時に状態を戻すなら、毎フレーム再主張するか相手を止める。
補足(同時に実測): Animator遅れ dFL 中央0.0028/最大0.0144 Unity単位 = 0.035/0.18 PMX単位。
  深貫入閾値0.5の1/3以下で、貫通の主因ではない(1フレーム遅れ自体は存在する)。
  刻みは fixedDeltaTime=0.02 に対し内部は蓄積式で1/30刻み(steps=0/1が交互)=設計通り。

## 髪/スカートのコマ落ち(ジャダー)の原因と対策 (2026-08-09)
症状: 髪の動きがカクカク/コマ落ちして見える。
原因: **物理の内部ステップが実時間で不均一**。Unityの FixedUpdate は `Time.fixedDeltaTime`(既定0.02s=50Hz)
間隔で呼ばれるが、エンジンは `FixedTimeStep`(既定1/30) のアキュムレータで刻むため、
1回のFixedUpdateで進む内部ステップ数が 0,1,0,1,1,0,1,... と周期的に変動する(実測ログの steps= と一致)。
結果、**物理は毎回33.3ms分進むのに、実時間の更新間隔は 20ms/40ms とバラつく**=ジャダー。
(さらに30Hz更新なので60fps表示では1姿勢が1〜2フレーム保持され、その保持数も交互に変わる)

**★2026-08-09 既定値を変更**: `MmdPhysicsBehaviour` の既定を `FixedTimeStep=1/60・SubSteps=1・AlignUnityFixedTimestep=ON` にした。
  変更したのは **Unityコンポーネントの既定値だけ**。以下は意図的に据え置き:
  - `PhysicsWorld` の既定 (1/30・SubSteps=2): 5つのハーネスが `StepSimulation(w.FixedTimeStep)` で回しており、
    変えると「1呼び出しで進む時間」が半分になりテストの意味が変わるため。
  - `BonePoseCsvPlayer` の 1/30・SubSteps=2: 1回の `StepSimulation(FixedTimeStep)` = CSV1フレーム(1/30秒)という
    前提で駆動しているため、1/60にすると再生が半速になりCSVと同期しなくなる。

対策(検証済み): **FixedTimeStep と Time.fixedDeltaTime を一致させ、毎FixedUpdate=ちょうど1ステップにする**。
推奨は `FixedTimeStep=1/60, SubSteps=1` + `Time.fixedDeltaTime=1/60`:
- **忠実度は完全一致**: 実効刻みが現行(1/30×2サブ)と同じ1/60のため、bonecheckが数値まで一致
  (傾き中央11.20 / p90 23.52 / 12窓比1.0611 = 現行と同一)。
- **CPUも同等**: 同一プロセス交互A/Bの最小値で 0.610ms vs 0.646ms (差はノイズ内)。同じサブステップ数だから当然。
- 実装: `MmdPhysicsBehaviour.AlignUnityFixedTimestep`(既定OFF)をONにすると起動時に自動整列+ログ。
  OFFのままでも整列していなければ起動時に1度だけ警告を出す。
※注意: `Time.fixedDeltaTime` はUnity全体の物理刻み。Custom運用ではPhysXはパーク済みなので実害はない。
※残る限界: 表示が60fpsを超える環境(120Hz等)では60Hz更新でも1姿勢が2フレーム保持される。
  完全な滑らかさが要るなら書き戻しの補間(Rigidbody.interpolate相当)が必要だが、
  「不均一さ」由来のジャダーは上記の整列で消える。

## バネのモーター行化 (SpringAsMotorRow) の採用 (2026-08-22)

`Joint.SpringAsMotorRow` の既定を **ON** にした。当エンジンのばねは陽的力積
(`ApplySprings` が `-k*err*dt` を直接 `ApplyImpulse` し、デッドビートでクランプ) だったが、
Bullet 2.75 は `btGeneric6DofSpringConstraint::internalUpdateSprings` で
ばね力を**リミットモーターの目標速度と最大力**に変換し、**ソルバ行として反復内で解く**。
構造的に別物であり、これが残っていた最大の実装差だった。

### 採用の根拠

**1. 行レベルで Bullet と等価であることを確認済み。**
ばね付きジョイントだけの最小網 (Joint 4本 / 剛体5個 / 接触ゼロ) に Bullet の状態を移植し、
同じ求解順で 1 サブステップぶんを突き合わせた結果:

| 量 | 最大相対差 |
|---|---|
| 行集合・順序 | 24行 一致 |
| effMass (実効質量) | 4.1e-07 |
| bias (目標速度) | 2.7e-04 |
| 累積力積 (10反復すべて) | 2.75e-04 |
| 構築時の相対速度 | 24/24 一致 |

いずれも float 丸めの範囲。**ばね側に残る実装差は無い。**

**2. 当てるパラメータをひとつも作っていない。**
係数は全て Bullet 実ソースの値をそのまま使う:
`velFactor = fps * springDamping / numIterations` の `springDamping` は Bullet 既定の **1.0**
(PMX はこの値を持たないので、つまみにせず Bullet 既定を使う)、
`getMotorFactor` の `timeFact = fps * erp` の `erp` は `Joint.Beta`。

**3. 採用ゲート全通過。**

| 主回帰 (compilecheck) | 全 PASS |
| tsbaseline ビット一致 | 10.995 / 22.064 / 112.203 — **不変** |

### ClampSpringImpulse の位置づけ

`ClampSpringImpulse` は **陽的経路 (`SpringAsMotorRow = false`) 専用の絆創膏**として残置する。

## ★台帳: 二層分類 (2026-08-23)

### ★摩擦合成方式の実証 — **MMD も「積」だった** (2026-08-23 決着)

`tools/fricprobe` の傾斜面試験 (傾いた板の上の箱が滑るか止まるか) をユーザーが
MMD/PmxEditor で観察した結果:

| ラウンド | 観察 | 読み |
|---|---|---|
| 第1 (tanθ=0.35/0.55/0.80 × 摩擦対2種) | **全6件 滑る** | 対B (0.5,0.5) が 0.35 で滑る = μ<0.35。候補で該当は **積 (0.25) だけ** |
| 第2 (tanθ=0.30/0.22/0.15/0.08) | **0.30 滑る / 0.22・0.15・0.08 止まる** | **μ = 0.22〜0.30**。「摩擦が効いていない (μ≈0)」の可能性を排除 |

→ **MMD/PMXe の摩擦合成は 積 `f0·f1`。Bullet 2.75 と同じ。**
   当エンジン既定の **幾何平均 `√(f0·f1)` の方が誤り**である。

★**そして、それが分かったことで新しい問題が立った。**
  もみあげ (`friction=0.5`) の正しい μ は 0.25。MMD はその μ で参照 (=1.00) を出す。
  当エンジンは同じ 0.25 にすると **2.24x** 動く。
  つまり **同じ摩擦係数でも当エンジンの方がよく滑る**。
  既定の幾何平均 (μ=0.5) は、その滑りすぎを **μ を倍にして相殺していただけ**だった。
  出力は合っていたが理由が間違っていた (スカートの幻と同じ構図。ただし今回は参照が正しい側)。

### 補正層フェーズへの調査項目 (登録)

- **★新スレッド: 同じ μ でも当エンジンの方がよく滑る。** もみあげで 2.24 倍。
  摩擦行の実装 (μPn の参照時点・接線方向・反復内の順序・warm-start) を
  **駆動姿勢で** bulletref と行レベルで突き合わせる。
  ここが解ければ `FRICMUL` を素直に採用でき、既定の幾何平均という相殺も外せる。
- 静止の微揺れにおける PMXe 補正層の往復ノイズの定量 (純Bullet の約10倍という値の内訳)。

### 運用注記: `bulletref` との突き合わせ

**寄り添い部を OFF にして行うこと。** 寄り添い部は定義上 Bullet と違うので、
入れたまま行レベルを突き合わせても差が出るのは当たり前で、比較の意味が無くなる。
具体的には少なくとも `SYMDIST=0` を明示する (v1 で既定 ON になったため、
env 未設定だと入ったままになる)。

## 登録フラグ (Bullet 実経路として正しいが、現時点では既定にしないもの)

以下は **却下ではない**。Bullet 2.75 の実挙動としては正しいと確認済みだが、
当エンジンに残る近似 (接触の受理閾値・margin・求解順序) との**組み合わせ収支**が
現時点で出力ゲートを通らない。残りの整合が進んだ時点で再評価する。

### `Joint.BulletAngleConvention` / `Joint.AngularMixedAxes` / `Joint.LinearLeverMode=1` (3点構成)

角度抽出の対象行列が転置していた件 (当方 euler(A⁻¹B) / Bullet euler(B⁻¹A)) と、
角度行の混合軸、並進行の Linear Torque Decoupling。**行レベルで Bullet と完全一致する**
(段(a)(b) とも、求解順まで揃えて最大 1.25e-05)。最小網の残留角速度は 52.67 → 0.857 deg/s (61分の1)。

不採用の理由: モデルB スカートの静止 |Δp| がモーター行単独の 3.84x に対し **6.86x** と悪化する。
31モデルでも中央 改善6 / 悪化9。

### `PhysicsWorld.BulletRotationIntegration` (ROTEXP)

姿勢積分。当エンジンは `q += 0.5*w*q*dt` の線形化更新だが、
Bullet 2.75 `btTransformUtil::integrateTransform` の実経路は**指数写像**である
(当方の式は Bullet のソースにも在るが `#ifdef QUATERNION_DERIVATIVE` で**無効化されている**分岐)。
誤差は θ³/24 毎ステップ (θ=|w|dt)。|w|=6 rad/s・dt=1/60 で 4.7e-5 rad/ステップ。
Bullet の状態を移植した突き合わせでは、姿勢の乖離が 4.69e-05 → **1.20e-07**、
1サブステップ後の速度差が 2.71e-03 → **1.51e-06** と 1000倍以上縮む。**正しさに疑いは無い。**

不採用の理由 — 出力ゲート2件で不通過:
- **31モデルスイープ**: モーター行単独から ROTEXP を足すと全ての列で悪化側へ振れる。

  | 列 | モーター行 単独 | ＋ROTEXP |
  |---|---|---|
  | 残留角速度 中央 | 改善8 / 悪化5 | 改善7 / **悪化10** |
  | 残留角速度 p90 | 改善16 / 悪化3 | 改善12 / 悪化12 |
  | 収束比 (後半/前半) | 改善13 / 悪化5 | 改善8 / **悪化13** |
  | 拘束違反 p90 | 改善10 / 悪化9 | 改善13 / 悪化11 |

  残留角速度 中央の悪化が大きい順に モデルP 13.3→**27.9** (拘束違反 0.075→**0.178**)、
  モデルY 63.2→74.2、モデルP(生足) 16.8→27.1、モデルB 34.4→38.7、
  モデルR 0.0→**3.4** (違反 0.069→0.123)。
  改善側もある (モデルT 31.4→26.0 / モデルO 40.1→35.1 / モデルS 47.0→42.7)。NaN・発散は 0件。
- **最小網**: 1房+横渡し の残留角速度 95.45 → **105.31** (+10.3%)。

**★指標が同一モデルで逆を向く例として記録する。** モデルB では
**スカートの |Δp| は改善 (3.84x→2.76x)** なのに **全動的剛体の |w| 中央は悪化 (98.6→112.1)**。
測っている量が違う (スカートのボーン変位 vs 髪を含む全剛体の角速度) 上に、
駆動ゲートでも ROTEXP は髪を 0.94→0.87 に減らしており、髪側で収支が反転している。
**「Bullet 実経路として正しい」ことは「当エンジンの現状に入れて良い」を意味しない。**
他の近似が残っている間は、正しさの積み増しが打ち消し合いを崩すことがある。

### `PersistentManifold.SymmetricBreakingDistance` (SYMDIST) — 2026-08-23 台帳登録

★**Bullet に無い機構**。2.75 も現行 3.x master も
`validContactDistance(pt) { return pt.m_distance1 <= getContactBreakingThreshold(); }` の
**片側**判定のままで、深い側の番人はどこにも無い。よって北極星 原則2 の
「登録済み逸脱 + 出力ゲート判定」の手続きで扱う。既定 OFF。

直している病理: 剛体が回ると保存済みローカル点が真の最近接から滑り、法線が凍結したまま
`d = (worldA-worldB)·normal` が**負へ暴走**する。真値「接触なし」のペアが d = -0.66 まで育ち、
その幻がそのまま接触 rhs に載る (NormalBias = 0.2*0.66*60 = 7.9)。
定常窓の接触行の **14% (22/154)** がこの幻だった。

### `Joint.BulletLimitRowGating` (LIMGATE)  — 2026-08-22 台帳登録

ロック軸の行を作るかどうかを Bullet の `testLimitValue` / `needApplyForce` に揃える。
**ロック軸 (lo==hi) でも、変位がちょうど限界値なら Bullet は行を作らない。**
当エンジンは無条件に行を立てていたので、Bullet が自由にしている瞬間に速度拘束を掛けていた。

ゲートの論理だけでは足りず、**判定に食わせる変位の計算鎖ごと**移植する必要がある
(`2fef84a`)。ロック軸は「変位が厳密に 0 か否か」で行の有無が決まるので、
1e-8 の残差の有無がそのまま拘束の有無に化ける。効くのは3箇所:
関節フレームの基底を**行列積**で作る (四元数積だと厳密な単位行列になり軸が割り切れる) /
原点も行列×ベクトル / 逆行列は転置ではなく**余因子**。**基底が主犯**で、余因子だけでは動かない。

実証済みの効果:
- **行レベル**: 移植姿勢の1サブステップで 全10反復 不一致0行・最大 2.39e-06 (力積尺度の 0.00005%)。
  バインド姿勢の frame0 行集合は **95/95 で完全一致** (両側とも差分ゼロ)。
- **静止3つ組** (フル現行スタック・JF無・反復10・3600F・3点あり):
  モデルA 髪 29.49x → **10.36x** (2.8倍改善・ただし依然 非収束)。
  モデルB スカート 0.71→0.73x / モデルP スカート 0.08→0.08x (維持)。ettc 髪 3.38→3.69x。

★**取り消した主張**: 是正前の LIMGATE は ettc 髪を 0.43x で収束させたが、
これはバインド姿勢で行が 95→58 本まで落ち、髪が1ステップ自由落下する
**キックによる幻**だった。是正後は 3.69x で非収束に戻る。
モデルA の 2.8倍改善だけが本物として残る。

現時点で既定にしない理由: 単独では出力ゲート一式を回していない。
残る乖離 (接触の貫入) と束ねて完全セットとして評価する。

## 教訓: A/B の「許容」を摂動だけで見積もってはいけない (2026-08-22)

drivedp の部位別比で「現既定から退行なし」を機械判定しようとして、
許容を**ウォームアップ摂動 (58〜62step) の幅**だけで見積もったところ、
もみあげ・アホ毛・前髪は摂動に**まったく反応せず許容が 0.000** になり、
**0.001 の動きまで退行と数えて「何も変えない」が最適解として選ばれる**という退化が起きた。

原因: 摂動法が測れるのは**カオス感度**だけで、**統計量そのものの標本不確かさ**を測れない。
2本しかない部位の中央値は、揺れなくても本質的に精度が低い。

対策: **ボーン標本のブートストラップ** (部位内のボーンをリサンプルして比の90%幅を取る) を加え、
2つを二乗和で合成して許容とする。

| 部位 | 本数 | カオス感度幅 (中央/p90) | ボーン標本90%幅 | 合成許容 |
|---|---:|---|---|---|
| もみあげ | 4 | 0.000 / 0.000 | 0.031 / 0.023 | 0.031 / 0.023 |
| アホ毛 | 2 | 0.000 / 0.000 | 0.030 / 0.003 | 0.030 / 0.003 |
| スカート | 64 | 0.032 / 0.018 | 0.161 / 0.082 | 0.164 / 0.084 |
| 前髪 | 6 | 0.001 / 0.000 | 0.028 / 0.020 | 0.028 / 0.020 |
| 胸 | 4 | 0.004 / 0.003 | 0.085 / 0.030 | 0.085 / 0.031 |
| 髪 | 14 | 0.019 / 0.044 | 0.077 / 0.057 | 0.079 / 0.072 |
| ﾈｸﾀｲ | 2 | 0.030 / 0.012 | 0.393 / 0.141 | 0.394 / 0.141 |

**★本数の少ない部位 (ﾈｸﾀｲ2本・アホ毛2本) は許容が広すぎて判別力が無い。**
これらの部位で優劣を主張してはいけない。

## 教訓: 静止の行レベル判定を「相対」で出してはいけない (2026-08-22)

★**この節は [NORTH_STAR.md](../NORTH_STAR.md) 1-d の要約である。矛盾したら NORTH_STAR.md が正。**

`bulletref` との行レベル突き合わせは、力積の p90 を尺度にした**相対**で合否を出していた。
静止の文脈ではこれが機能しない。

タスク60 の実測 (純Bullet が50秒かけて落ち着いた姿勢を移植し、1ステップだけ回して比較):

| 物差し | 出た数字 | 読み |
|---|---|---|
| ジョイント行の力積 (相対) | 反復9で不一致5行・最大 6.9e-03 = 尺度 2.39 の 0.29% | 「ほぼ一致」 |
| 1ステップ後の平均 \|w\| (絶対) | 純Bullet 0.031 → 当エンジン 0.132 | **4.3倍** |

静止では参照側の残差がほぼ 0 なので、**相対で無視できる差が絶対では桁になる**。
以後、静止の突き合わせは尺度を**その系の残差**に取る。行が合っても状態量が合わなければ不一致。

## 指標の階層 — 採否を決めてよいのは参照アンカー付きの |Δp| だけ (2026-08-22)

★**この節は [NORTH_STAR.md](../NORTH_STAR.md) の要約である。矛盾したら NORTH_STAR.md が正。**

### 判定者 (採否を決めてよい)
参照との**比**が取れるものに限る。`BoneDp`(静止) / `drivedp`(駆動) / `bulletref`(純Bullet) /
`bonecheck`・`hairfid`(駆動忠実度)。比の読み方は **1.00 = 参照と同じ量。0 が正解ではない。**

### スクリーニング (採否を決めてはいけない)
31モデルの `restosc` スイープ (残留角速度 |w| ・拘束違反) には**参照アンカーが無い**。
用途は **NaN・発散・粗い退行 (桁で悪化していないか) の検出**に限る。

### 格下げの理由
**1. タスク6 の教訓がスイープへ適用されていなかった。**
「揺れ物は止まるのが正解」ではない。参照 (PMXエディタ) 自身が揺れている。
参照値を知らずに |w| の大小を比べるのは **暗黙にゼロと比較している**のと同じ。
静止 |Δp| の側では是正済みだったが、スイープ側に適用が漏れていた。

**2. 実際に符号が矛盾した。** 同じ変更・同じモデル・同じ剛体集合で逆を向いた:

| 対象 | \|w\| | 参照アンカー付き \|Δp\| |
|---|---|---|
| モデルA の髪 (受理閾値 ON) | 67.9 → 61.4 (改善) | 0.0290 → 0.0390 (**悪化**) |
| モデルA_ettc髪 (同上) | 54.2 → 68.6 (悪化) | 0.0257 → 0.0208 (**改善**) |

|w| は「小さいほど良い」というゼロ基準なので、参照より静かになっても改善と出る。
**動かなさすぎも不正解**である以上、判定者にはできない。

上の「登録フラグ (Bullet 実経路として正しいが、現時点では既定にしないもの)」節に書いた
不採用理由のうち、**31モデルスイープを根拠にしている部分はこの階層化により無効**である。
